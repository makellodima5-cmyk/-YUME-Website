# YUBERA Support Page and Telegram Stars Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a dedicated YUBERA support page matching the supplied mobile references, place a compact support card between the home hero and Popular, and make the visible payment outcome depend on the server-confirmed Telegram Stars transaction.

**Architecture:** Keep the existing TanStack Start, React, Tailwind/CSS, Cloudflare D1 and Telegram Bot API design. Reuse the existing `yume_stars_donations` table, initData validation, invoice creation route, webhook and `openInvoice`; add an authenticated status endpoint keyed by a server-generated opaque invoice payload, and render a dedicated support screen through the app’s existing `section=support` view state so the shared header and bottom navigation remain intact. Do not build a second payment subsystem or alter the Cloudflare cache/Worker topology.

**Tech Stack:** React 19, TanStack Start/Router, TypeScript, Tailwind CSS, Lucide, Cloudflare Workers/D1, Telegram Mini Apps API and Telegram Bot API (XTR).

**Spec:** User-provided YUBERA support requirements and two supplied mobile screenshot references (2026-11-10).

## Global Constraints

- Preserve existing homepage structure; add only one support card between hero and Popular.
- Support card click navigates only; it must not create an invoice or trigger payment.
- Use Telegram Stars currency `XTR`; invoice amounts are integer Stars and created server-side.
- Validate `Telegram.WebApp.initData` server-side; do not use `initDataUnsafe` as authentication and do not expose bot tokens to the frontend.
- Confirm paid status only from verified Telegram `successful_payment` webhook processing and persisted D1 state; `openInvoice` callback status is not authoritative.
- Verify Telegram user, payload, currency, amount and unique `telegram_payment_charge_id`; duplicate webhook delivery must not create duplicate paid records.
- Preserve existing five-item bottom navigation and mark Main active on the support route.
- Keep Cloudflare D1/R2/Workers/Queues and existing Telegram bot configuration; no new payment provider or infrastructure.
- Preserve dark graphite surfaces, restrained grey borders, white/grey typography, YUBERA orange accents and gold Stars artwork. No purple styling.
- Keep six amount choices in a 3 × 2 grid: 50, 100, 250, 500, 1000 and Other; default 100.
- Use the already present support banner asset `/images/yubera-stars-donation-bg.webp` if its composition suits the screenshot; no new image hosting/loading system.
- Respect mobile safe areas, vertical scrolling, fixed existing navigation, reduced motion and narrow screens.
- Never claim production payment flow is verified merely because unit tests/build pass; live Bot API/webhook configuration needs a real Telegram Mini App test.

## Review Focus

- A Telegram invoice callback says `paid` before the webhook arrives: UI must remain pending and poll the server status.
- Duplicate/replayed successful_payment update with same payload/charge: payment record remains single and no second success transition occurs.
- Wrong Telegram user, currency or amount for a payload: reject pre-checkout and never mark paid.
- A custom amount is empty, fractional, unsafe, negative or out of allowed server limit: no invoice is created and the UI explains the correction.
- Payment status endpoint receives another user's payload or expired initData: disclose no payment data and return an authentication/authorization error.
