# План переноса YUME с Cloudflare на Beget VPS

**Статус:** план подготовки; код не изменён, VPS ещё не создан.  
**Дата фиксации решения:** 22 октября 2026 г.  
**Основание:** аудит main, текущая конфигурация репозитория, предпусковые документы YUME и выбранная пользователем карточка тарифа Beget.

## 1. Решение по целевой инфраструктуре

Выбран стартовый VPS Beget, локация Санкт-Петербург:

| Параметр | Выбранное значение |
|---|---|
| vCPU | 2 ядра, 3–3,3 ГГц по карточке тарифа |
| RAM | 4 ГБ |
| Диск | 40 ГБ NVMe |
| Сетевой канал | 1 Гбит/с по карточке тарифа |
| ОС | Ubuntu 24.04 LTS |
| Публичный IPv4 | Включён |
| Цена на экране создания | 990 ₽/мес. сервер + 150 ₽/мес. IPv4 = 1 140 ₽/мес. |
| Отдельная БД | На старте не планируется |
| Статус | Конфигурация выбрана; VPS пока не создан |

Цена и конфигурация зафиксированы по скриншотам панели пользователя, а не по созданному и оплаченному VPS. Итоговый счёт нужно сверить с панелью непосредственно перед заказом. Домен AnimeYume.ru ещё не считается купленным.

Официальные материалы Beget:
- VPS и конфигурации: https://beget.com/ru/vps
- Ubuntu 24.04 в каталоге: https://beget.com/ru/cloud/marketplace/ubuntu-24-04
- Резервное копирование VPS: https://beget.com/ru/kb/manual/rezervnoe-kopirovanie-vps

Наличие серверной площадки в России важно для выбранной архитектуры, но само по себе не означает автоматического соответствия всей обработки требованиям 152-ФЗ. По фактическому договору нужно подтвердить юридическое лицо провайдера, обработку журналов, резервные копии, права доступа и условия обработки данных.

## 2. Что есть в репозитории сейчас

Текущая версия всё ещё ориентирована на Cloudflare, поэтому это не перенос готового каталога файлов на VPS.

- React 19, TypeScript, TanStack Start.
- Vite и Nitro; конфигурация из @lovable.dev/vite-tanstack-config использует Cloudflare как целевую среду по умолчанию.
- vite.config.ts внешним импортом оставляет cloudflare:workers.
- src/server.ts использует Worker-форму обработчика fetch(request, env, ctx) и передаёт runtime env в модуль каталога.
- src/data/catalog-d1.server.ts импортирует cloudflare:workers и получает binding YUME_DB; ниже по коду используется API D1 (prepare, bind, first, all, run, batch).
- wrangler.jsonc указывает Worker entry, .output/public, и D1 binding YUME_DB.
- package.json имеет команду deploy:cloudflare, но не имеет production-команды запуска Node-сервера.
- .github/workflows/cloudflare-worker.yml проверяет Worker build, D1 binding и Wrangler deploy artifact.
- src/data/territorial-restrictions.server.ts определяет страну через request.cf.country или заголовок CF-IPCountry.
- Каталог из Shikimori хранится в D1; инициализация рассчитана на 1 000 записей. Обложки и баннеры хранятся не в D1: база хранит URL.
- На текущем этапе регистрация, серверные аккаунты, Premium, рекламные блоки и полнофункциональный видеоплеер не считаются реализованными. Избранное и «Мой список» сохраняются в localStorage браузера.

Источники в репозитории: vite.config.ts, wrangler.jsonc, src/server.ts, src/data/catalog-d1.server.ts, src/data/shikimori.ts, src/data/territorial-restrictions.server.ts, package.json, .github/workflows/cloudflare-worker.yml, migrations/0001_create_anime_catalog.sql, docs/project-status.md.

## 3. Принцип переноса базы каталога

**Данные из Cloudflare D1 переносить не будем.** На целевом VPS создаём новую пустую БД, создаём схему и заново наполняем каталог запросами к Shikimori. Старую D1 не экспортируем и не импортируем.

При этом не выбрасываем модель данных приложения: поля, маппинг и фильтры каталога нужно сохранить или осознанно изменить. Схема каталога уже отражена в migrations/0001_create_anime_catalog.sql и CREATE_SCHEMA_STATEMENTS файла src/data/catalog-d1.server.ts.

### Предлагаемая БД для старта

Предварительный вариант — SQLite-файл на том же VPS. Он подходит по масштабу небольшого каталога и близок к используемому D1 SQL-диалекту; это позволяет избежать оплаты отдельного сервера БД. Это **архитектурная рекомендация для прототипа**, а не уже принятое изменение кода. Перед реализацией следует проверить выбранную Node.js-библиотеку, конкурентные записи и атомарность заполнения каталога.

Отдельная PostgreSQL-система может потребоваться позднее, если появятся серверные аккаунты, пользовательская библиотека, много одновременных записей или потребность в отдельном обслуживании БД. В текущий запуск её не добавлять без отдельного обоснования.

### Поведение первого заполнения

1. При запуске пустой БД приложение создаёт таблицы и индексы.
2. Наполнение выполняется через существующую интеграцию Shikimori; данные D1 не копируются.
3. Ограничение каталога (около 1 000 записей) сохраняется, пока не будет принято отдельное решение его менять.
4. Ошибки API, HTTP 429, неполный результат, повторный запуск и одновременные запросы должны быть безопасно обработаны.
5. Маркер «каталог готов» записывается только после успешного завершения заполнения. В противном случае UI показывает штатное сообщение о временной недоступности.
6. Порядок заполнения и результат проверяются тестом на чистой пустой базе.

## 4. Что нужно изменить в коде перед переносом

Это план работ, не выполненные изменения.

### P0 — приложение должно запускаться на Node.js

1. **Целевая сборка Nitro.** Настроить и проверить preset node_server (точное место настройки — в конфигурации Nitro/Vite с учётом текущего плагина). Убедиться, что bun run build выдаёт автономный Node server output и что он запускается локально командой node .output/server/index.mjs.
2. **Production scripts.** Добавить/уточнить start, команду проверки здоровья и воспроизводимые команды установки, сборки и запуска. Сборка должна использовать версию Node.js, поддерживаемую выбранной версией Nitro; исходный CI уже использует Node 22.
3. **Серверный entry point.** Пересмотреть src/server.ts: Worker-аргументы env и ctx не должны требоваться как обязательное окружение Node. Сохранить согласованную обработку ошибок SSR и совместимый entry point TanStack Start.
4. **Слой базы данных.** Удалить жёсткую зависимость рабочего каталога от cloudflare:workers и binding YUME_DB. Вынести доступ к каталогу за server-only адаптер/интерфейс; реализация для VPS должна использовать локальную БД. Клиентский bundle не должен включать драйвер БД или путь к файлу базы.
5. **SQL и транзакции.** Сопоставить методы D1 с выбранной библиотекой SQLite; отдельно проверить подготовленные запросы, батчи/транзакции, обработку дат и JSON-полей, индексы и маркер заполнения. Не считать одинаковый SQL-грамматический стиль полной совместимостью API.
6. **Путь к данным и права.** Файл БД должен находиться в постоянном каталоге вне временной папки сборки и директории релиза, с ограниченными правами доступа. Не хранить его внутри .output или перезаписываемого каталога деплоя.
7. **Переменные окружения.** Перенести настройки в серверное окружение/защищённый env-файл. Не коммитить секреты, пароли, приватные ключи и токены. Добавить безопасный .env.example только с названиями и пояснениями.
8. **Статические ресурсы.** Проверить, что Node/Nitro раздаёт собранные файлы .output/public, а все маршруты, SSR, server functions и динамические страницы работают за reverse proxy.

### P0 — геоограничение

9. **Убрать зависимость от Cloudflare country metadata.** После прямого переноса на Beget request.cf.country и доверенный Cloudflare-заголовок не будут доступны автоматически. Текущий код не должен молча считать отсутствие кода страны допустимым признаком успешной геопроверки для production.
10. **Выбрать способ определения страны.** Для прямого подключения к VPS предпочтительно рассмотреть GeoIP-базу на сервере, включая процесс безопасного обновления базы. Истинный IP должен определяться только из доверенной сетевой конфигурации. Если сохраняется внешний proxy/CDN, нужно отдельно описать доверенные диапазоны proxy и оценить правовые последствия обработки трафика этим поставщиком.
11. **Сохранить серверную фильтрацию.** Ограничение должно оставаться на сервере для каталога и прямой страницы тайтла; обновить тесты RU / не-RU / неизвестная страна и проверить Cache-Control: private, no-store для ответов с геозависимой выдачей.
12. **Не расширять автоматически список запретов.** Существующий список из трёх ID — начальная техническая конфигурация, а не полный официальный перечень. Это отдельный правовой/контентный процесс, не часть миграции хостинга.

### P0 — CI/CD и запуск на VPS

13. **Развести проверку и production deployment.** Текущий workflow жёстко проверяет Cloudflare Worker-артефакт и YUME_DB. Для Node-цели нужно добавить/перестроить CI: тесты, lint, Node/Nitro build и проверку запуска. Не выключать текущую цепочку до создания проверенной Node-сборки и согласованного окна переключения.
14. **Перепроверить GitHub deployment.** Нынешняя публикация связана с Cloudflare; она не деплоит приложение на Beget. Потребуется отдельная безопасная схема доставки на VPS (например, SSH/rsync с ограниченным ключом или иной выбранный способ), секреты только в GitHub Actions secrets, deployment user без root-доступа.
15. **Управление процессом.** Запускать приложение под отдельным системным пользователем, через systemd или проверенный Docker deployment. Для минимального VPS предварительно проще рассмотреть systemd; Docker не обязателен только потому, что доступен в маркетплейсе.
16. **Reverse proxy и TLS.** Настроить Nginx или Caddy перед Node-приложением; приложение слушает localhost/private interface, наружу открываются только нужные порты. После покупки домена настроить DNS, HTTPS, редирект на HTTPS и проверку обновления сертификата.
17. **Сеть и доступы.** Firewall: публичные 80/443; SSH ограничить доверенными IP, где возможно. Использовать SSH-ключи, запретить парольный root-вход, обновлять ОС/зависимости и не публиковать порт БД.
18. **Логи и контроль здоровья.** Настроить ротацию логов, проверку живости приложения, уведомления при заполнении диска/RAM и ошибках запуска. Не писать в логи секреты и лишние персональные сведения.

### P1 — резервирование и восстановление

19. **Не полагаться только на автоматический backup VPS.** Документация Beget говорит, что файловые резервные копии VPS создаются с периодичностью в несколько дней, хранятся ограниченное время и не гарантируют согласованную копию работающей БД. Нужно сделать тестовое восстановление.
20. Для SQLite предусмотреть корректную копию согласованного состояния средствами SQLite (или остановить приложение на время снимка), а затем копировать архив отдельно от каталога приложения. Проверить восстановление на тестовом экземпляре.
21. Каталог можно повторно заполнить с Shikimori, поэтому импорт D1 не нужен. Тем не менее сохранить рабочий способ восстановления схемы и наполнения; решить, нужен ли дополнительный backup файла каталога после успешной инициализации.
22. Зафиксировать способ отката приложения на предыдущий release и резервный план возврата DNS/старой публикации. Не считать rollback рабочим, пока он не проверен.

## 5. Порядок работ

### Фаза A — до покупки VPS (локальная подготовка)

- [ ] Аудит всех ссылок на cloudflare:workers, YUME_DB, request.cf, CF-IPCountry, Wrangler и Cloudflare deployment.
- [ ] Уточнить Node/Nitro target без изменения production и сделать отдельную тестовую сборку.
- [ ] Выбрать SQLite-драйвер и способ хранения файла; подтвердить совместимость текущего SQL.
- [ ] Зафиксировать стартовую процедуру seed и тест чистой БД.
- [ ] Подготовить отдельный CI build для Node-цели.

### Фаза B — после создания VPS

- [ ] Подтвердить локацию/договор Beget и параметры фактически созданного VPS.
- [ ] Установить обновления Ubuntu, Node.js, Bun (если нужен для сборки), reverse proxy и firewall.
- [ ] Настроить пользователя deployment, секреты окружения, директории приложения и данных.
- [ ] Развернуть staging/тестовую версию без переключения постоянного домена.
- [ ] Проверить TLS, логи, автоматический запуск после перезагрузки, backup и восстановление.
- [ ] Заполнить новую базу заново с Shikimori и проверить целостность/количество записей.

### Фаза C — проверка перед переключением

- [ ] Проверить главную, каталог, фильтры, поиск, сортировку, пагинацию и страницу тайтла.
- [ ] Проверить RU / не-RU / неизвестную страну на реальном механизме GeoIP.
- [ ] Проверить мобильную и десктопную версии, трейлеры YouTube и внешние сетевые запросы.
- [ ] Провести нагрузочный тест и измерить CPU, RAM, latency, ошибки и время первого заполнения каталога.
- [ ] Проверить перезапуск процесса и сервера, заполнение диска, восстановление backup и откат.
- [ ] Только после успешных проверок согласовать домен/DNS и окно переключения.
- [ ] После переключения перепроверить реальный production URL отдельно от CI.

## 6. Нагрузочная цель

Фраза «до 1 000 пользователей» пока не задаёт проверяемую нагрузку: 1 000 посетителей за сутки и 1 000 одновременных пользователей принципиально различаются. Конфигурация 2 vCPU / 4 ГБ / 40 ГБ — разумная бюджетная стартовая точка для проверки, но не обещание выдержать 1 000 одновременных сессий.

До широкого запуска нужно задать профиль: посетители/сутки, пик одновременных запросов, доля SSR и частота обращения к Shikimori. На первом этапе проверить постепенную конкурентную нагрузку и повышать ресурсы только по измерениям.

## 8. Критерии готовности миграции

Миграция считается технически готовой только когда:

- production build запускается на Node.js без runtime-модулей Cloudflare;
- каталог работает через новую локальную БД и успешно наполняется с нуля;
- не осталось критических runtime-зависимостей от D1/Wrangler/Cloudflare;
- геофильтрация проверена серверными тестами и на staging;
- CI проверяет Node target;
- HTTPS, процессный менеджер, firewall, логи, backup и restore проверены;
- основные маршруты прошли регрессионный и нагрузочный тест;
- документация и правовые черновики приведены к фактически работающей инфраструктуре;
- пользователь отдельно согласовал переключение production.

**Ограничение текущего документа:** код не изменялся; VPS не создавался; сборка под Node и запуск на Beget пока не проверены. Этот документ фиксирует план, а не отчёт о состоявшейся миграции.
