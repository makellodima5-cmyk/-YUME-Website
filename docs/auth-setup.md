# YUME: настройка авторизации через VK ID и Яндекс ID

Документ описывает серверный OAuth-поток через VK ID / Яндекс ID и регистрацию в Cloudflare D1. Владелец сообщает, что авторизация активна, однако этот документ указывает, что без необходимых переменных окружения кнопки провайдеров отключены. Это расхождение нужно закрыть проверкой production: подтвердить активного провайдера, переменные окружения, callback URL и успешный вход/регистрацию. Не публиковать этот документ как доказательство активной конфигурации без такой проверки.

## Переменные окружения Cloudflare Worker

Задайте переменные в настройках Worker / Secrets. Секреты не следует коммитить в репозиторий.

- \`YUME_AUTH_SESSION_SECRET\` — секрет подписи OAuth-state и временного подтверждения провайдера. Не менее 32 случайных символов.
- \`YUME_PUBLIC_ORIGIN\` — публичный HTTPS origin сайта без пути, например \`https://your-domain.example\`.
- \`VKID_CLIENT_ID\` — ID приложения VK ID.
- \`VKID_REDIRECT_URI\` — точный callback URL, зарегистрированный в приложении VK ID: \`https://your-domain.example/api/auth/vk/callback\`.
- \`YANDEX_CLIENT_ID\` — ID приложения Яндекс OAuth.
- \`YANDEX_CLIENT_SECRET\` — секрет приложения Яндекс OAuth.
- \`YANDEX_REDIRECT_URI\` — точный callback URL, зарегистрированный в приложении Яндекс OAuth: \`https://your-domain.example/api/auth/yandex/callback\`.

Замените \`your-domain.example\` на фактический домен YUME. Если используются разные домены Preview и Production, для каждого окружения должны быть согласованы свои зарегистрированные callback URL и конфигурация.

## Что происходит при регистрации

1. Пользователь заполняет дату рождения и ставит обязательную галочку согласия с Политикой конфиденциальности.
2. Пользователь начинает OAuth через VK ID или Яндекс ID. Сервер использует OAuth state и PKCE, обменивает код на токен и запрашивает идентификатор профиля у провайдера.
3. Только после успешной серверной проверки браузер получает подписанное временное подтверждение провайдера в cookie HttpOnly.
4. Кнопка «Зарегистрироваться» активна только при корректной дате рождения, отмеченном согласии и действующем подтверждении провайдера.
5. При отправке формы сервер повторно проверяет все условия и только после этого записывает пользователя в \`yume_users\`; факт согласия, версию политики и дату рождения сохраняет сервер. Создаётся отдельная серверная сессия.
6. Отказ провайдера, просроченное подтверждение, отключённый провайдер или отсутствие галочки не приводят к созданию пользователя.

Идентификатор провайдера берётся из ответа провайдера на сервере. Значение, присланное браузером, не считается доказательством авторизации. Токены провайдеров не записываются в таблицу пользователей.

## Таблицы

- \`yume_users\` — внутренний ID пользователя, провайдер и его стабильный ID, дата рождения, дата и версия согласия.
- \`yume_sessions\` — хеш токена сессии и срок её действия; исходный токен хранится только в cookie браузера.

Схема создаётся на сервере при первом обращении к auth-потоку. SQL-миграция \`migrations/0002_create_yume_users.sql\` сохранена для управляемого применения схемы.

## Проверка фактической конфигурации перед публикацией

Владелец сообщает, что авторизация активна, но из этого документа не видно, какие именно переменные настроены в текущем Production. Подтвердите активного провайдера и успешный end-to-end сценарий на production URL; проверьте отказ/отмену, повторную регистрацию, истечение временного подтверждения, отсутствие согласия, выход, срок действия сессии и удаление аккаунта. Не переносите секреты в репозиторий и не публикуйте их в отчётах.
